# bpm-backend 后端简化方案

> 状态：方案待评审，尚未实施
> 范围：仅 `bpm-backend/`。`bpm-backend-deploy/` 为部署快照，按工作区规则**不参与改动**。
> 依据：通读全部应用代码（约 690 行）并核对了 `bpm-frontend/src/utils/dataOption.ts` 的实际调用契约。

---

## 1. 结论摘要

后端功能正确，但**结构性重复**明显：同一套「从 B 站拉取合集 → 落库 Collection → 落库 Video」的逻辑在三个端点中各写了一遍（其中两遍几乎逐行相同）；8 个路由处理器各自包裹一层相同的 `try/except` 样板；「更新合集」采用"删库重建"策略，因此派生出了状态快照、二次删除、二次创建等一串中间函数。

合理重构后：应用代码约 **690 行 → 460~480 行**（省 30%），且大部分改动**不需要动前端契约**。

| 指标 | 现状 | 目标 |
|---|---|---|
| 应用代码总行数 | ~691 | ~470 |
| `router.py` | 366 | ~150 |
| 合集同步逻辑实现份数 | 3 | 1 |
| 路由内 try/except 样板 | 8 处 | 0（收敛到全局处理器） |
| 「更新合集」所需中间函数 | 3（快照/删除/重建） | 0（原地 upsert） |

## 3. 问题清单（按收益排序）

### P1｜同一套「合集同步」逻辑写了三遍 ★最高收益

涉及端点：

| 端点 | 位置 | 说明 |
|---|---|---|
| `POST /collection` | `router.py:52` `create_collection` | 基础流程 |
| `POST /collection/update` | `router.py:250` `update_collection` | 基础流程 + 观看状态保留 |
| `POST /collections/batch-update` | `router.py:308` `batch_update_collections` | 对上面那套逻辑再套一层 for 循环 |

三者的核心段落（拉取 → 建 Collection → `for idx, episode in enumerate(episodes)` 建 Video → `model_dump` → 拼装返回值）**逐行相同**，约 30 行 × 3 = 90 行冗余。

更关键的是「更新」走的是**删库重建**：

```
update_collection_to_db()      # 快照所有视频的 watched_count / status，并取出 bvid、created_at、order_index
        ↓
delete_collection_to_db()      # 删掉整个合集（级联删视频）
        ↓
get_collection_data_and_episodes(bvid)   # 用旧 bvid 重新请求 B 站
        ↓
create_collection_to_db() + create_video_to_db()   # 重建，并回填观看状态
```

连带产生的问题：

1. **每次刷新都在做全量删除+全量插入**，MySQL 里外键级联删除 + 自增/索引维护，代价远高于原地 `UPDATE`。
2. `collection_service.py:57` 用 `orm_videos[0].bvid` 作为种子去请求 B 站。若该合集的视频已被 UP 下架导致列表为空，直接 `IndexError` → 500。
3. 拿**旧 bvid** 反查合集，若该视频被移动/合集的代表视频发生变化，可能解析到另一个 `season_id`，造成"更新 A 却写入了 B"。
4. `created_at` / `order_index` 需要手工搬运，任何一处忘搬就丢数据（`order_index` 靠手工回填）。
5. 函数名 `update_collection_to_db`（`collection_service.py:69`）实际**不写库**，只是读取快照，名不副实。

### P2｜路由层 try/except 样板重复 8 处

- `delete_single_collection`（`router.py:112`）、`update_video`（`router.py:219`）、`get_collections`（`router.py:157`）中 `except Exception as e:` 的 `e` **完全未使用**。
- `update_video` 中 `raise HTTPException(detail=e)` 直接把异常**对象**塞进响应体（应为 `str(e)`），FastAPI 会尝试序列化它。
- 每处都重复 `"系统繁忙，请稍后再试"` 字面量。

这属于横切关注点，应交给全局异常处理器。

### P3｜`GET /collection` 手工 join + 字典分组

`get_all_collections_from_db`（`collection_service.py:36`）返回 `List[Tuple[Collection, Video]]`，路由再手工塞字典（`router.py:157-195`，约 20 行）。

附带缺陷：`select(Collection, Video).join(...)` 是 **INNER JOIN**，没有视频的合集会被静默丢弃；空结果时路由特意返回 `data: null`，而前端 `dataOption.ts:53` 又要 `Array.isArray` 兜底——两端各写一次特判。

### P4｜`PATCH /video` 请求模型过重

`UpdateVideoStatusRequest.videos: List[Video]`（`router.py:37`），但 `video_service.py` 只取 `video.bvid`（`video_service.py:32`）。等于要求前端上传完整视频对象只为传 bvid 列表。另外 `option: int` 的 0/1/2 是裸魔法数字。

### P5｜模型层每列双份声明

`models/collection.py`、`models/video.py` 中每列同时写 SQLModel `Field(...)` 和 SQLAlchemy `Column(...)`，信息重复，且把 `from sqlalchemy import ...` 全都拽了进来。

### P6｜杂项坏味道（均已逐条验证）

| 位置 | 问题 |
|---|---|
| `config.py:25-27` | `DEBUG` / `APP_TITLE` / `APP_VERSION` 定义后全仓无引用 |
| `database.py:2` | `from contextlib import contextmanager` 未使用 |
| 两个 service 第 1 行 | `Optional` 导入未使用 |
| `video_service.py:23` | 返回注解 `-> [Collection, List[Video]]` 是**列表字面量**，非法类型注解（应为 `Tuple[...]`） |
| `main.py:9` | `len(logger._core.handlers) <= 1` 依赖 loguru 私有 API |
| `utils/bilibiliApi.py:16` | 同步 `requests.get` 阻塞 async 事件循环，且**未设 timeout** |
| `router.py:246` | `update_video` 成功响应 message 写成"获取合集信息成功"（复制粘贴错误） |
| 路由命名 | `/collection` 与 `/collections` 单复数混用 |

## 5. 逐项改造方案

### 5.1 【P1】合并为唯一的同步入口

在 `collection_service.py` 新增：

```python
from typing import Any, Dict, Optional
from datetime import datetime

from sqlmodel import Session, select

from models.collection import Collection
from models.video import Video
from utils.bilibiliApi import get_collection_data_and_episodes


def sync_collection_from_bilibili(
    session: Session,
    bvid: str,
    *,
    if_exists: str = "error",  # "error" -> 重复添加报 400；"update" -> 原地刷新
) -> Collection:
    """拉取 B 站合集并落库。创建与更新共用同一实现。

    update 模式下：合集字段原地更新，视频逐条 upsert，
    未在新列表中的视频被删除；watched_count / status / created_at / order_index 自然保留。
    """
    collection_data, episodes = get_collection_data_and_episodes(bvid)
    season_id = collection_data["season_id"]

    collection = session.get(Collection, season_id)
    if collection and if_exists == "error":
        raise ValueError("该合集已存在，请勿重复添加")

    if collection:
        collection.title = collection_data["title"]
        collection.total_episodes = collection_data["total_episodes"]
        collection.up_name = collection_data["up_name"]
        collection.last_sync_at = datetime.now()
    else:
        collection = Collection(**collection_data)
        session.add(collection)

    session.flush()

    old_videos = {
        v.bvid: v
        for v in session.exec(
            select(Video).where(Video.collection_id == season_id)
        ).all()
    }

    kept_bvids = set()
    for idx, episode in enumerate(episodes):
        ep_bvid = episode["bvid"]
        kept_bvids.add(ep_bvid)

        video = old_videos.get(ep_bvid)
        if video is None:
            session.add(
                Video(
                    bvid=ep_bvid,
                    title=episode["title"],
                    duration=episode["arc"]["duration"],
                    collection_id=season_id,
                    order_index=idx,
                )
            )
            continue

        # 原地更新，保留 watched_count / status
        video.title = episode["title"]
        video.duration = episode["arc"]["duration"]
        video.order_index = idx

    # 下架 / 移出合集的视频
    for ep_bvid, video in old_videos.items():
        if ep_bvid not in kept_bvids:
            session.delete(video)

    session.flush()
    session.refresh(collection)
    return collection
```

于是三个端点退化为：

```python
# POST /collection
collection = sync_collection_from_bilibili(session, request.bvid, if_exists="error")
session.commit()
return ok("合集创建成功", serialize_collection(collection))

# POST /collection/update
collection = sync_collection_from_bilibili(session, request.bvid, if_exists="update")
session.commit()
return ok("合集更新成功", serialize_collection(collection))
```

批量接口对每项开一个 SAVEPOINT，避免单项失败污染整个会话（现状是循环中出错后仍统一 `commit`，可能提交半成品）：

```python
for season_id in request.season_ids:
    try:
        with session.begin_nested():
            collection = sync_collection_from_bilibili(session, season_id, if_exists="update")
            succeeded.append(serialize_collection(collection))
    except Exception as e:
        logger.exception(f"批量更新失败: season_id={season_id}")
        failed.append({"season_id": season_id, "error": "更新失败"})
```

> ⚠️ 兼容性提示：`batch-update` 的入参目前是 `season_ids`，但 `sync_collection_from_bilibili` 需要的是 **bvid**（要拿去请求 B 站）。现状能工作是因为它从库里取 `orm_videos[0].bvid` 当种子——这正是 P1 里第 2、3 条缺陷的根源。改造后应改为按 `season_id` 查库取一个代表 bvid：
>
> ```python
> sample = session.exec(
>     select(Video).where(Video.collection_id == season_id).order_by(Video.order_index).limit(1)
> ).first()
> if sample is None:
>     raise ValueError("合集内没有视频，无法刷新")
> bvid = sample.bvid
> ```
>
> 这样既修掉 `IndexError`，也让"用哪个 bvid 请求"有确定语义，并保持对前端 `season_ids` 契约不变。

**删除的函数**：`update_collection_to_db`（`collection_service.py:69`），以及 `create_collection_to_db` / `delete_collection_to_db` 中仅被 update 流程使用的那部分组合调用。

### 5.2 【P2】全局异常处理器替代路由样板

`main.py` 增加：

```python
from fastapi.responses import JSONResponse

@app.exception_handler(ValueError)
async def handle_value_error(request, exc: ValueError):
    return JSONResponse(
        status_code=400,
        content={"status": "error", "code": 400, "detail": str(exc)},
    )

@app.exception_handler(Exception)
async def handle_unhandled(request, exc: Exception):
    logger.exception(f"未处理异常: {exc}")
    return JSONResponse(
        status_code=500,
        content={"status": "error", "code": 500, "detail": "系统繁忙，请稍后再试"},
    )
```

要点：

- 保留 `detail` 键，因为前端 `dataOption.ts` 统一读 `responseData.detail`。
- `HTTPException` 由 FastAPI 内建处理，路由内不再需要 `except HTTPException: raise`。
- 业务层的 `ValueError`（如"该合集已存在"、"非法 option"）自动转 400，替代原来手写的 `HTTPException`。

### 5.3 【P3】列表接口去掉手工分组

推荐方案 A（两查询 + 一次分组，无 ORM 关系陷阱）：

```python
def get_all_collections(session: Session) -> List[Collection]:
    return session.exec(
        select(Collection).order_by(
            Collection.order_index,
            Collection.created_at.desc(),
            Collection.season_id,
        )
    ).all()


def get_videos_map(session: Session, season_ids: List[int]) -> Dict[int, List[Video]]:
    videos = session.exec(
        select(Video)
        .where(Video.collection_id.in_(season_ids))
        .order_by(Video.order_index, Video.bvid)
    ).all()
    grouped: Dict[int, List[Video]] = {sid: [] for sid in season_ids}
    for v in videos:
        grouped[v.collection_id].append(v)
    return grouped
```

优点：不丢空合集、两查询搞定、无 N+1、不引入序列化递归风险。

可选方案 B：模型加 `Relationship` + `selectinload`。**注意**：加了关系字段后 `model_dump()` 会带出 `videos` 造成嵌套/递归，序列化必须显式 `exclude={"videos"}`。若采用，请一并引入 `serializers.py` 统一出口。

同时把空结果统一为 `[]`，可删掉 `router.py` 的 `data: None` 特判与前端 `dataOption.ts:53` 的兜底（前端那一行可保留作为防御，不算必须改）。

### 5.5 【P5】模型精简

```python
class Collection(SQLModel, table=True):
    __tablename__ = "collections"

    season_id: int = Field(primary_key=True, sa_column_kwargs={"comment": "合集ID"})
    title: str = Field(max_length=100, sa_column_kwargs={"comment": "合集标题"})
    total_episodes: int = Field(sa_column_kwargs={"comment": "合集总集数"})
    up_name: str = Field(default="", max_length=16, sa_column_kwargs={"comment": "UP主名称"})
    order_index: int = Field(default=0, sa_column_kwargs={"comment": "排序索引"})
    created_at: datetime = Field(
        sa_column_kwargs={"server_default": text("CURRENT_TIMESTAMP"), "comment": "创建时间"}
    )
    ...
```

注意 `total_episodes` 原为 `SmallInteger`、`duration` 原为 `MEDIUMINT`，若去掉显式 `Column` 会退回默认 `INT`。**改列类型在 MySQL 里是 DDL 变更**，因此这两列建议**保留显式 `sa_column`**，其余列精简。这样既降低噪音，又不触发迁移。

## 8. 验证方案

当前仓库**没有测试框架**。建议本次重构同时补齐最小回归集。

### 8.1 手工冒烟（必须全部覆盖）

1. 添加新合集 → 校验 `collections` / `videos` 行数与 B 站一致，`order_index` 连续。
2. 重复添加同一合集 → 返回 400「该合集已存在，请勿重复添加」。
3. 对已有合集做 `+1 / -1 / 标记部分观看` → 刷新进度保持。
4. 刷新合集（update）→ **观看次数与状态不丢**，`created_at` 与 `order_index` 不变。
5. 拖拽排序 → 重启后顺序保持。
6. 单个删除 / 批量删除 → 关联视频级联删除。
7. 批量更新（含一个不存在的 season_id）→ 部分成功、失败项出现在 `failed` 中。
8. 传入非合集视频的 bvid → 400「该视频不是合集内容」。

## 9. 风险与回归重点

| 风险 | 等级 | 缓解 |
|---|---|---|
| 原地 upsert 与"删库重建"语义差异 | **高** | 必须回归 8.1 第 3、4 条；对比改造前后同一合集的 `videos` 表快照 |
| `session.refresh` / flush 时序导致返回旧对象 | 中 | 序列化前统一 `session.refresh(collection)`，并在 commit 后重新查询一次拼装响应 |
| 关系字段引入序列化递归 | 中 | 采用 5.3 方案 A（不引入 Relationship）可完全规避 |
| 移除显式 `Column` 触发 MySQL DDL | 中 | 仅精简非类型敏感列，保住 `MEDIUMINT` / `SmallInteger` / `CHAR(12)` |
| 全局 `Exception` 处理器掩盖真实错误 | 低 | 处理器内 `logger.exception` 保留堆栈 |
| 批量更新 savepoint 行为在 MySQL 下差异 | 低 | 用 `begin_nested()`（SAVEPOINT），InnoDB 支持良好 |
